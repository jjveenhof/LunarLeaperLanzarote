# QGIS -- decisions a successor cannot re-derive from the code

Why things are the way they are, for facts a successor cannot re-derive from the code,
from `README.md`, or from opening the project and looking. Most of the real work here
lives in `.qgz` projects, shapefiles, and rasters under `QGIS project/` -- data,
outside git, opaque to a successor who can't just read source. This file is the durable
record of how that layer of the project was actually built and which parts are
load-bearing for published figures. See `README.md` for "what is true now"; this file is
"why," and for the QGIS-project items below, also "how it was fixed."

---

## `FieldworkReporting.qgz` is the sole live project -- do not resurrect `Research module report.qgz` (2026-08-11)

Despite its name suggesting the opposite, `Research module report.qgz` is a stale,
broken artifact: last saved February, 8 of its 10 layers point at a `../La Corona Cave/`
folder that no longer exists anywhere in the tree (renamed to `LiDAR La Corona/` at some
point), zero print layouts, none of the overburden/DTM/GPR-line work. `FieldworkReporting.qgz`
is the one with all 35 real layers and all 7 print layouts, 4 of which are thesis figures.

The docs previously named the broken file as "main active project" -- a straightforward
documentation error, now fixed, but the fact that a file named "Research module report"
is the DECOY and a file named "FieldworkReporting" (which sounds like a superseded
earlier draft) is the REAL one is exactly the kind of thing a successor will get
backwards by guessing from names alone. (Audited 2026-08-11:
finding [1].

## A layer's NAME is not proof of its SOURCE -- verify, don't assume (2026-08-11)

Found and fixed: the layer named `cavetop_clean_masked_LaGente` in `FieldworkReporting.qgz`
was wired to `cavetop_clean_LaGente.tif` -- the RAW, pre-mask file -- not the actual masked
file. The correctly-masked file existed on disk the whole time but was referenced nowhere
in the project; it was saved but never loaded as a layer. This fed two live print-layout
map items, both of which ARE thesis figures (`main.tex:358-359`).

**Verified result, stated plainly so it doesn't get re-litigated:** the delivered thesis
PDFs (`thesis-overleaf/Maps/NWFieldworkArea.pdf`, `OverviewFieldworkAreaNoLegend.pdf`)
were checked against the fix and are visually correct -- the published figures were never
wrong. The bug only mattered for anyone re-opening the project and re-exporting those
layouts, which would silently have produced the unmasked raster (with the jameo-edge
specks that were specifically masked out) despite the layer's own name claiming
otherwise. Fixed via PyQGIS `setDataSource` (see tooling entry below); pre-fix backup was
kept and diffed, then deleted once the fix was confirmed and approved.

**The general lesson:** when auditing or extending this project, check a layer's
`<datasource>`/`source`, not just its display name, before trusting it -- a rename in the
QGIS layer panel does not repoint the underlying file, and nothing in the UI flags the
mismatch. This is the second time a QGIS layer-vs-file mismatch has bitten this project
(the first is the copy-paste gotcha in `README.md`'s overburden recipe) -- both are the
same underlying trap: QGIS lets a layer's label and its actual data source drift apart
silently.

## `QGIS project/Legacy/` is quarantine, not a reference source (2026-08-11)

Planning-stage shapefiles (`All GPR surveys.shp`, `ContextLine*`, `CentreLines*`,
`FlowerPetalLine*`, and ~10 more) plus the two unused `Fieldworkplanning*.qgz` projects
were moved there after confirming via PyQGIS that none of them are referenced anywhere in
`FieldworkReporting.qgz`. They carry decision history (early survey planning), which is
why they were moved, not deleted (rule 5). **Do not load anything from `Legacy/` into the
live project as a shortcut** -- if a layer there looks useful, treat that as a sign the
live project's real equivalent should be found instead, not that the legacy one should be
resurrected.

## The overburden rasters are a manual GUI product -- this is a decision, not a gap (2026-08-11)

`cavetop_clean_masked*.tif` (full cave, Puerta Falsa, La Gente) cannot be regenerated by
running anything. The recipe (align surface onto ceiling grid -> subtract -> burn jameo
mask to nodata) is fully written out in `README.md`'s Rasters section and every input file
is present, so a successor CAN verify and manually reproduce them -- but there is no
script, and one was deliberately not written. Scripting the QGIS GUI workflow (Align
Rasters, the Processing raster calculator, GDAL Rasterize) into PyQGIS is real new
engineering effort, not a refactor, and was out of scope given the timeline. **If
bit-for-bit reproduction is ever required, budget GUI time (roughly 15-20 min per area),
do not go looking for a script that does not exist.**

## Tooling: the conda env has no GDAL/rasterio; use the OSGeo4W install instead (2026-08-11)

`GPR_plotting_LL` (this project's env) has neither `rasterio` nor `osgeo`/GDAL, so raster
CRS/statistics cannot be inspected from that Python. This machine has a separate QGIS
install via OSGeo4W at `C:\OSGeo4W\`, which bundles everything needed for QGIS-project
scripting:
- `C:\OSGeo4W\bin\gdalinfo.exe`, and GDAL's Python tools (`gdal_edit.py` etc.) under
  `C:\OSGeo4W\apps\Python312\Scripts\` -- for raster CRS/stats without touching the conda env.
- `C:\OSGeo4W\bin\python-qgis-ltr.bat` -- launches Python with PyQGIS (`qgis.core`) on the
  path. This is how the layer-rewire fix above and the layout re-export/comparison were
  done headlessly and precisely, instead of hand-editing zipped project XML or driving the
  GUI. `QgsApplication([], False)` + `initQgis()` + `QgsProject.instance().read(path)` gets
  a script-controlled handle on any `.qgz`; `QgsLayoutExporter` renders a named layout to
  PDF for comparison without opening the app.

**Do not conclude "no GDAL in this env" means raster verification is impossible** -- it
means use the OSGeo4W install instead. This was not obvious and cost real time to find the
first time.

## Hand-parsing `.qgz`/`.qgs` XML with regex is unreliable for attribute order (2026-08-11)

`.qgz` files are zip archives containing QGIS project XML -- readable directly (`zipfile`
+ regex/`re`), and that is how the phase-1 audit found the two findings above. But a raw
regex like `<Layout name="([^"]+)"` silently misses a layout if that particular `<Layout>`
tag happens to serialize with attributes in a different order (QGIS does not guarantee
attribute order is stable across every `<Layout>` element in a project) -- this is exactly
how the phase-1 audit initially missed one of the two stale references in the finding
above, and it was only caught by re-scanning more robustly during the 2026-08 cleanup.

**If parsing `.qgz` XML again: either use an attribute-order-independent match (find the
tag, then search for `name="..."` anywhere inside it, don't anchor to position), or better,
use PyQGIS itself (`QgsProject.read()`) rather than raw XML -- it resolves this and
everything else about the format correctly by construction.**

## `goldenmaster.py` tracks only the two `GPR_*.geojson` outputs, nothing about the QGIS project (2026-08-12)

The golden master here (`Code/QGIS/goldenmaster.py`) exists solely to catch a
silent formatting/logic drift in `points_to_lines.py`'s output. It does NOT and cannot
cover the QGIS project itself (rasters, layer styling, print layouts) -- there is no
script that produces those, so there is nothing to snapshot around (see the overburden
entry above). `test_goldenmaster_coverage.py` asserts the golden master's SOURCES glob
covers everything `points_to_lines.py` actually declares as output
(`OUTPUT_FILES` in that script) -- it deliberately does NOT scan `Data/GNSS/Cleaned/`
directory contents, because that folder also holds the two input CSVs, which are not and
should not be tracked; a directory scan would false-positive on them every run.

## Cross-folder data contracts: none exist here (2026-08-12)

Checked per `REFACTOR.md` phase-3 item 3b (the schema-assertion test), which is explicitly
scoped to Grav and GPR reading `Data/LiDAR/lidar_line{3,5}.csv`. QGIS's own outputs
(`GPR_Lines.geojson`, `GPR_FlowerPetals.geojson`) are consumed only by the QGIS project
itself, not by another session's Python -- no other session's code reads anything this
session writes, or vice versa. **3b does not apply here; no schema-assertion test was
added, deliberately, not by omission.**
